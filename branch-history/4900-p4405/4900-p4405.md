## Rationale

Implement D4405 (P4405), "prove and diagnose evaluation semantics": the two
semantics exist everywhere a semantic can be named, and an evaluation with
`prove` is an error, one with `diagnose` a warning, "contract assertion
cannot be proven", unless a proving strategy proves its predicate.  This
commit adds the strategy interface and its dispatcher but no strategy, so
every evaluation is diagnosed; `4910-p4405-fold` adds the first.
Neither has any run-time effect: the predicate is never evaluated, as for
`ignore`.  `-fcontracts-p4405` (implied by `-fcontracts-p3850`) admits
`prove` (8) and `diagnose` (9) -- the next free values after
`noexcept_enforce`, not the paper's 5 and 6 -- to every contract's allowed
set (`contract_base_allowed_mask`) and predefines `__cpp_contracts_prove`.
Without the flag, naming either on the command line, in a configuration or
with `-fcontract-group-evaluation-semantic=` gets the P4298-style warning
(`c_common_post_options`) and resolves as `ignore`.  The diagnose warning is
the new `-Wcontract-unproven`, on by default; libstdc++ gains the two
enumerators and the default handler their names, and `is_nonthrowing`
counts both.

The two semantics form a new category: active, but with no run-time check.
A contract with `ignore` or `assume` is dropped early; one with `prove` or
`diagnose` stays active until the point where its check would be emitted,
`emit_check_for_semantic`, which emits nothing and calls
`diagnose_unproven_contract` instead.  That describes the evaluation in a
`contract_proof_query` and makes the one call
`contract_diagnose_unless_proven` (`c-family/contracts-prove.h`, shared
with the C front end): it asks each enabled strategy in the registry
(`contracts-prove.cc`), each defined in a file of its own behind
`contract_proof_strategy`, and diagnoses the evaluation when none proves
it -- "contract predicate is always false" when one shows the predicate
false.  A proof is sound, or conditional when it relies on an earlier
assertion that is not guaranteed to hold (a strategy records whether it may
depend on such assumptions); both suppress the diagnostic.  So a callee-side evaluation is
diagnosed in the function body, once per template instantiation, and
nothing is diagnosed under `-fsyntax-only` (`p4405-template.C`,
`p4405-syntax-only.C`).  A caller-side evaluation is diagnosed by
`maybe_contract_wrap_call` at the call itself, with a note at the predicate,
-- the query carrying the call and the callee's parameters, so that a
strategy may use the arguments of a precondition -- and then counts as
`ignore`, so it neither makes a wrapper be built nor is
diagnosed again in one built for another contract
(`p4405-caller-side*.C`).  A specialization's contracts are substituted
only when its definition is instantiated, after the call, so for one that
is not yet substituted the query carries a private substitution of the
predicate, made with `tf_none` and never installed on the specialization
(`contract_for_caller_side_proof`); a precondition its requires-clause
discards is not evaluated, and a predicate that cannot be substituted (one
holding a lambda or a statement expression, a dependent one with captures,
one that fails) is marked opaque in the query, which no strategy is asked
to prove.  A call of an inheriting constructor is a call of
the constructor it inherits, so that constructor's caller-side evaluations
are diagnosed at each call of the inheriting one, with its arguments
(`diagnose_inheriting_ctor_call`); the call of the inherited constructor in
the inheriting constructor GCC defines diagnoses nothing
(`p4405-caller-side-inheriting.C`).  A call in an unevaluated operand is
not diagnosed, and one in a contract predicate is evaluated only if a check
evaluates the predicate, which is not known where the predicate is parsed:
its evaluations are diagnosed where a check of the predicate with an
evaluating semantic, or a dynamically selected one, is emitted
(`diagnose_checked_predicate_calls`, `p4405-predicate-call-checked.C`).  Everywhere nothing would be diagnosed -- constant
evaluation, the initialization of postcondition captures, the value a P3595
dynamic selector returns -- the pair behaves exactly as `ignore`
(`p4405-constexpr*.C`, `p4405-post-captures*.C`,
`p4405-dynamic-selector*.C`).

The interface also lets a strategy prove later in the compilation, as
`4920-p4405-shadow`'s proof shadows do.  Such a strategy may answer
`CPR_DEFERRED` for an evaluation the front end marked deferrable; nothing
is diagnosed then, and `contract_diagnose_unless_proven` hands the front
end the strategy's marker to place where the evaluation happens.  The
strategy's other hooks say whether it may defer evaluations in a function
(`contract_proof_defers_p`), give the statement that lets it assume an
earlier evaluation's predicate (`contract_proof_assumption`), and may take
over the diagnostics decided at once so that all of them come out in order
later.  A query and an assumption may belong to an override pair
(`override_pair`, the assumption's `pair`): an evaluation made for one of
D4405R0's override pairs, whose diagnostic a strategy takes over even when
it is not enabled (`4920-p4405-shadow`, `4940-p4405-override`), made in the
pair's override shadow or, as an obligation of the overriding function
itself, in its ordinary one (`override_shadow`).  The C++ emission points use them: the callee-side one places the
marker in place of the check, with the predicate as a check there would
evaluate it (`contract_check_condition`); a plain check of any other
semantic is followed by the assumption (`add_contract_proof_assumption`);
and a caller-side precondition's marker, built with the call's object for
the placeholder `this`, comes before the call, or the wrapper call.  A
constructor or destructor call, or one returning a class, must stay a call
for its users (`build_cplus_new`, `AGGR_INIT_EXPR`, cleanups): one whose
object exists carries the marker in its object argument, evaluated before
the call too -- and an automatic variable's initialization by a constexpr
constructor call folded to a constant keeps it (`expand_default_init`,
`contract_object_proof_markers`); a call that initializes a temporary (one
returning a class, or a constructor call for a placeholder object) is made
that temporary's `TARGET_EXPR` at once, with the marker ahead of the call
in its initializer, the shape the comma operator gives
(`contract_proof_markers_p` recognizes the markers there for
`extract_call_expr` and `[[nodiscard]]`).  A precondition naming `this`
at a call for a placeholder object, which has no object yet, is given
that temporary's slot, the temporary being made first for it; an
initialization that elides the temporary replaces the slot in the markers
by the object it initializes (`cp_gimplify_init_expr`).  The same temporary is how a caller-side wrapper of a constructor is
called for a placeholder object: its `AGGR_INIT_EXPR` calls the wrapper in
place of the constructor, so the temporary's slot is still what it is
passed (`build_value_init` keeps that temporary; constant evaluation
treats the call as constructing, `constructing_call_p`; the wrapper is
never redirected to a base constructor, `make_base_init_ok`).  No marker is offered in a module or a coroutine, nor for a
postcondition with captures.  A strategy may also want to know which
function bodies hold an evaluation whose code lets the optimizers take its
predicate to hold -- a check with `enforce` or `noexcept_enforce` (a
noreturn entry point) or `quick_enforce` (an inline trap), or an
`assume` assumption -- and that another translation
unit's evaluation of the same assertion need not make
(`contract_proof_note_premise`): `build_contract_check` notes each plain
one, unless the assertion's label admits only the terminating semantics
and `assume` (`contract_premise_settled_p`), which a caller-side
evaluation in a wrapper never is, `ignore` being always admitted there.
With no strategy deferring, none of this changes anything.

Most of the compiler-side change is teaching existing machinery about the
new category, and those lines sit in the commits that wrote that machinery:
the enumerators, their names, `contract_semantic_proving_p`, the extended
`CES_ALL_ALLOWED_WITH_EXTENSIONS` and the best-fit walk
(`contracts-config.h`/`.cc`) and `contract_semantic_has_no_runtime_check`
with its uses in `contract_active_p`, `contract_constexpr_ignored_p` and the
dynamic-dispatch adjustment are `2400-p3595`'s; the capture predicate is
`4000-p3098`'s, the `compute_semantic` range check `4220`'s, the
`allowed_semantics` probe bound `4200-p3400-core`'s, `is_nonthrowing`'s
classification `4800-p4298`'s, the P3100 implicit-assertion mapping
`6000-p3100-core`'s, and the C front end's support (`c-parser.cc`, with the
`gcc.dg/contracts/c-p4405-*.c` tests) `5000-p4299`'s.  The best fit puts
both at `ignore`'s level, where `ignore` is preferred, then `diagnose`,
then `prove`: a `prove` that is not allowed becomes `diagnose`, failing
that `ignore`, a `diagnose` becomes `ignore`, failing that `prove`, and any
other semantic whose walk reaches the level with `ignore` not allowed
becomes `diagnose`, failing that `prove` -- so a label allowing only `prove`
(D4405's `always_prove`) works whatever the build configures
(`p4405-labels*.C`).  P3100 implicit assertions do not allow
them, so a configuration naming them resolves those to `ignore`
(`p4405-p3100-unaffected.C`), and `-fsanitize-semantic=` rejects them
through its allowed-set check (`p4405-sanitize-semantic*.C`).  What this
commit itself holds is what is P4405's alone: the flag, warning and macro,
the base-mask gate, the two diagnostic sites and their helper, the proving
interface and dispatcher, the library
enumerators, the documentation, and the tests.  The libstdc++ tests
`evaluation_semantic_set.cc` and `labels_semantic_restriction.cc` pin the
whole of `evaluation_semantic_set::all()`, which now holds the pair, so they
land here rather than with `4800-p4298`.

`is_continuing` names its continuing semantics rather than negating
`is_terminating` -- `unspecified`, `ignore`, `observe`, `noexcept_observe`,
`prove` and `diagnose` -- in the classification block
`4200-p3400-core` writes.  P3400 [support.contract.control.semfun] allows a
semantic to be neither terminating nor continuing, and `assume` is one,
since continuing after a violation under it is undefined behaviour.  The
test of every semantic's classification names the P4405 enumerators, so it
lands here (`p3400-is-continuing.C`).

## Compile gap

**Behaviour gap: `-fcontracts-p4405` does not yet imply `-fcontracts`.**  As
for every per-paper flag, the `LangEnabledBy` expression that turns the base
facility on names all of them at once and lands in
`6900-cross-paper-options`, so until then `-fcontracts-p4405` sets only its
own variable.  This commit's tests pass `-fcontracts` explicitly, except
`p4405-umbrella.C`, which tests the umbrella flag's implication and cannot
pass before `6900`.  `p4405-p3100-unaffected.C` and
`p4405-sanitize-semantic*.C` need `-fcontracts-p3100`, and
`p4405-labels-always.C` `-fcontracts-allow-assume`, and so cannot run
before `6000-p3100-core`.

**Compile gap: the warning for C reads `flag_contracts_p4299`.**  The
no-flag warning in `c_common_post_options` is gated on the language's
contracts flag, `flag_contracts` in C++ and `flag_contracts_p4299` in C, and
the latter is declared by `5000-p4299`, the next paper.  The condition is
one expression, so it cannot be cut on the paper boundary; until
`5000-p4299` this commit does not compile `c-opts.cc`.

Nothing else is owed.  Every identifier the P4405 lines elsewhere use is
declared at or before their commit: the enumerators and
`contract_semantic_proving_p` with `2400-p3595`'s `contracts-config.h`,
`contract_semantic_has_no_runtime_check` with `2400`'s helpers.  The two
`EnumValue` rows for `prove` and `diagnose` share `4800-p4298`'s piece of
the `-fcontract-evaluation-semantic=` table (its `EnumValue` markers are
byte-identical, so no cut can separate them); from `4800` to here they are
accepted spellings that the best fit, which `2400` already teaches about
them, resolves to `ignore` -- without the warning this commit adds.
