## Rationale

Implement P4283, "Requires Clauses for Contract Assertions": a contract
assertion may carry a `requires (...)` clause, evaluated before the
predicate, that discards the whole contract when unsatisfied instead of
making it ill-formed.  This entry lays the two pieces that stand on their
own before anything else can use them; the pieces that thread a
requires-clause through construction, redeclaration matching and template
substitution are separate commits later in this same band
(`4620-contract-extension-fields`, `4630-label-and-requires-parsing`,
`4640-contract-substitution-plumbing`), each of which lists this one as a
dependency.

* **`contract_constraint_satisfied_p`** (`constraint.cc`) is the
  satisfaction entry point a requires-clause on a contract needs, and it is
  not `constraints_satisfied_p`: a contract's requires-clause is an
  arbitrary constraint-logical-or-expression -- a conjunction, disjunction,
  negation or a lone atomic constraint -- not a single concept-check, so it
  has to be normalized with `normalize_constraint_expression` before
  `satisfy_normalized_constraints` will accept it.  Because the expression
  handed in is already substituted for the current instantiation, its atoms
  carry concrete arguments and satisfaction runs with empty args.

* **`cp_parser_contract_requires_clause`** (`parser.cc`) parses the clause
  itself: if `-fcontracts-p4283` is off, or the enclosing function is not a
  template, it diagnoses and skips to recover; otherwise it defers to the
  pre-existing `cp_parser_requires_clause_opt` with `lambda_p=true`, so that
  the `(` beginning the contract's own predicate is not mistaken for a
  postfix call on the constraint.  That `lambda_p` reuse is why
  `cp_parser_constraint_requires_parens` needs one more case here: a `[`
  immediately following the constraint must also end the tentative parse
  the way `(` already does, since P4283 and P3098 can appear on the same
  contract and a capture list opens with `[`.  This is the one place the
  change is not purely additive -- `lambda_p=true` already has a real,
  pre-existing caller (a constrained generic lambda's own requires-clause,
  `cp_parser_lambda_declarator_opt`), so the new `[` case is live for that
  caller too, not only for a contract.  It has no observable effect there in
  practice: a generic lambda's requires-clause is followed by its body,
  which opens with `{`, not a bare `[`.

## Compile gap

`cp_parser_contract_requires_clause` is defined here but not yet called from
anywhere: the two call sites -- inside `cp_parser_contract_assert` and
`cp_parser_function_contract_specifier`, immediately after the label is
parsed -- belong to `4630-label-and-requires-parsing`, which depends on this
commit for exactly the function it wires up.  On its own, this commit would
leave a `static` function defined and unreferenced, which trips
`-Wunused-function` under the `-Werror` a GCC bootstrap builds with; the
scaffolding a standalone build needs is a throwaway call to it (or an
unused-attribute mark), and `4630` is what replaces that with the real
integrated call.

`contract_constraint_satisfied_p` has the same shape but no such warning: it
is `extern`, and its one real caller -- inside `tsubst_contract`, testing the
substituted requires-clause before the captures or the predicate are
instantiated -- is part of the single 152-line insertion
`4640-contract-substitution-plumbing` makes to that function, described in
that commit's own Rationale.  Until `4640`, `contract_constraint_satisfied_p`
compiles and is simply never invoked; that is a silent, not a loud, gap --
nothing here would tell a reader that a requires-clause is parsed but never
consulted, except that `CONTRACT_REQUIRES_CLAUSE` (the storage for it) does
not exist until `4620-contract-extension-fields` either, so there is nowhere
yet for a parsed requires-clause to even be kept.

This is a targeted check of the specific call graph this entry's Contents
names, not an exhaustive search of every other `lambda_p=true` or
concepts-satisfaction call site in `parser.cc` and `constraint.cc` for a
second, unnoticed interaction.

**Behaviour gap: `-fcontracts-p4283` does not yet imply `-fcontracts`.**  The
`LangEnabledBy` expression that turns the base facility on is a single
boolean naming every per-paper flag at once, so it cannot be divided and
lands in `6900-cross-paper-options`.  Until that commit, `-fcontracts-p4283` sets its
own `flag_contracts_*` variable and nothing else, and this commit's own
tests -- which compile with it and expect contracts to be enabled -- fail.
The code is right; only the switch that arms it is missing.
