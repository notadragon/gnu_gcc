## Rationale

Implement P3097, "Support for Virtual Functions" -- adopted into the working
draft at the Brno meeting, so this is the one commit in the 3000 band whose
checker-facing behaviour is closest to final wording rather than a paper
still moving through committee.

Before this commit, GCC's contracts implementation (like the base P2900
support it extends) flatly rejects a contract on a virtual function:
`check_for_override` (`gcc/cp/class.cc`) calls
`error_at (..., "contracts cannot be added to virtual functions")` whenever
`DECL_HAS_CONTRACTS_P` is set on an overriding declaration.  This commit's
one-line change to that check -- gating the error on `!flag_contracts_p3097`
-- is the actual grant of the feature.  Everything else here is what has to
be true for a virtual function's contracts, once permitted, to be checked
against the right override.

The mechanism is the caller-side contract-wrapper machinery already present
in GCC's base contracts support: at a call site, `maybe_contract_wrap_call`
can interpose a small wrapper function that copies the callee's contracts
and checks them, so the compiler-generated call goes through the wrapper
instead of the real function directly.  For a virtual function that wrapper
cannot simply call the statically named override -- P3097's two-source model
requires the call to dispatch dynamically, so that whichever override is
actually selected at runtime is the one whose (potentially different)
callee-side contracts run.  Three changes make that possible:

* `build_over_call` (`call.cc`), which already knows the moment it is about
  to rewrite a direct call into a vtable dereference, now stashes the
  original (pre-rewrite) `FUNCTION_DECL` in a local and threads it down to
  `build_cxx_call` as `orig_fndecl` -- a parameter that already existed for
  an unrelated purpose (recovering the resolved decl behind a call to an
  overloaded target-multiversioned built-in).  The two uses cannot collide:
  a virtual member function is never a built-in, and the built-in-specific
  consumer is guarded on `fndecl_built_in_p`, while the P3097 consumer
  requires `DECL_IOBJ_MEMBER_FUNCTION_P` and `DECL_VIRTUAL_P`.  Target
  multiversioning of a virtual function, the one shape that could in
  principle mean both at once, is rejected outright with `sorry ()` on every
  FMV-capable target.  `build_cxx_call` turns the presence of `orig_fndecl`
  into a new `is_virtual_dispatch` bool and passes it on to
  `maybe_contract_wrap_call`; that function's own body, and the caller-side
  semantic-tuple logic it uses to decide whether a wrapper is even needed,
  belong to `2400-p3595`, which precedes this commit in the linear history
  and already carries the branch that checks
  `is_virtual_dispatch && flag_contracts_p3097`.

* `define_contract_wrapper_func`, the function that builds a wrapper's body,
  grows a `lookup_base` / `build_base_path` / `build_vfn_ref` sequence that
  builds a vtable call in place of the previous direct call when the wrapped
  function is virtual -- so the wrapper's own call dispatches dynamically,
  exactly as the call it replaces would have.  Because a virtual callee can
  now need more than one wrapper (a different caller-side semantic tuple can
  be attached per call site), the old single-wrapper-per-callee map-traversal
  callback is renamed to `define_one_contract_wrapper_func`, and a new
  `define_contract_wrapper_func` walks the `TREE_LIST` of wrappers now
  recorded against each callee, invoking the renamed function once per
  entry.  `count_wrapper_pairs` replaces the old `elements ()` count in
  `emit_contract_wrapper_func`'s progress check, since one callee can now own
  several map entries instead of exactly one.

* `maybe_define_contract_wrapper` is new: it lets a constexpr evaluation
  materialize a wrapper's body on demand, the first time it is needed,
  rather than waiting for the normal end-of-TU emission.
  `cxx_eval_call_expression` (`constexpr.cc`) calls it when evaluating a call
  to a function whose `DECL_CONTRACT_WRAPPER` body is not yet defined --
  the situation a constexpr virtual function carrying a contract would
  otherwise hit, being "used before its definition" in a constant
  expression.

The one documentation-only touch is `cp_build_function_call_vec`'s comment in
`typeck.cc`, updated to record that its own `orig_fndecl` parameter carries
the same dual meaning as `build_cxx_call`'s -- worth a reviewer's second
look precisely because no in-tree call site currently exercises it that way;
the parameter is defaulted and every caller omits it.

## Compile gap

This commit's own code is otherwise self-contained: `build_over_call`,
`build_cxx_call`, and the parameter addition to `maybe_contract_wrap_call`
only touch functions that already exist, either upstream or in
`2400-p3595`, which precedes this commit -- except for one real forward
reference.

`define_one_contract_wrapper_func` (the renamed body of the old
`define_contract_wrapper_func`) opens by calling
`maybe_instantiate_contracts (DECL_ORIGIN (fndecl))` to substitute a
class-template member's contracts before copying them into the wrapper.
That function's declaration (`gcc/cp/contracts.h`) and definition
(`gcc/cp/pt.cc`) both belong to `4020-instantiate-on-use`, a commit later in
this history that itself lists `3000-p3097` as a dependency.  On its own,
this commit needs a declaration (`extern void maybe_instantiate_contracts
(tree);`) and a stub -- and the stub can be a genuine no-op rather than an
approximation: `4020`'s real implementation itself early-returns unless the
decl is a template instantiation whose contracts have not yet been
substituted from its pattern, which is not the case this paper is actually
about (an ordinary, non-template virtual function).  The one shape where a
no-op stub would silently differ from the real function is a wrapper built
around a declaration-only class-template member function whose contract is
still written in terms of the pattern's own parameters -- there, the stub
would leave the wrapper's copied predicate dependent instead of substituted.
`4020-instantiate-on-use` replaces the stub.

**Behaviour gap: `-fcontracts-p3097` does not yet imply `-fcontracts`.**  The
`LangEnabledBy` expression that turns the base facility on is a single
boolean naming every per-paper flag at once, so it cannot be divided and
lands in `6900-cross-paper-options`.  Until that commit, `-fcontracts-p3097` sets its
own `flag_contracts_*` variable and nothing else, and this commit's own
tests -- which compile with it and expect contracts to be enabled -- fail.
The code is right; only the switch that arms it is missing.
