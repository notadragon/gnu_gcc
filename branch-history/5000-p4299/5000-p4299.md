## Rationale

Implement D4299, "C++ Contracts for C": add `_Pre`, `_Post` and
`_ContractAssert` to the C front end, a genuinely separate language surface
from everything else in this history, sharing only the runtime.  The three
keywords are contextual, gated behind `-fcontracts-p4299` via the
`D_C_CONTRACTS` mask on their reserved-word table entries in `c-common.cc`
(`contracts-keywords-no-flag.c` checks they are ordinary identifiers
without the flag), and are parsed by new `c_parser_contract_assert` and
`c_parser_contract_specifiers` (`c-parser.cc`) built for C's grammar rather
than adapted from the C++ parser: K&R declarators
(`contracts-kandr-pre.c`), parameter-declarator scoping
(`contracts-param-declarator-leak.c`, `contracts-proto-leak.c`), and
multiple or nested contracts on one function
(`contracts-multi-pre.c`, `contracts-nested-post.c`,
`contracts-nested-post-enclosing.c`) each needed their own handling.  A
postcondition's result name is supported and its misuse diagnosed
(`c_parser_diagnose_misplaced_result_name`,
`contracts-result-name-misplaced.c`, `contracts-post-no-result.c`,
`contracts-post-void-implicit.c`), and the check itself is injected at both
an explicit `return` (`c_maybe_check_postconditions`, called from
`c_finish_return` in `c-typeck.cc`) and a `void` function's implicit return
(the `finish_function` hunk in `c-decl.cc`), mirroring the C++ front end's
two injection points with C's own bookkeeping
(`c_clear_postconditions`/`c_clear_postconditions_for`,
`c_has_active_postconditions`).  A `contract_query` type
(`get_ns`/`get_caller_ns`) gives C the same P3595 dynamic-configuration
query surface as C++, reusing the shared `contracts-config.h`/`.cc`
machinery rather than duplicating it.

The one deliberately C-specific piece of runtime plumbing is
`maybe_emit_c_hcv_alias` (`c-decl.cc`): if a translation unit defines a
function named `handle_contract_violation` with signature
`void(const contract_violation_t *)`, it emits a same-body alias
`__handle_contract_violation`, so C gets picked up by the identical
weak-symbol dispatch libcontracts already uses for the C++ overload of the
same name (`contracts-handler-alias.c`) -- the same "just define this name"
ergonomics as C++, without C having overloads to resolve against.

C shares the entire runtime with C++ rather than getting its own: the
`gcc/gcc.cc` driver change here makes `-fcontracts-p4299` auto-link
`-lcontracts`, so a plain `.c` file needs no explicit `-l`/`-L`
(`contracts-implicit-link.c` proves exactly that, with no library flags in
its `dg-options`).  The bulk of the roughly 40 new `gcc.dg/contracts/` tests
duplicate the g++.dg contract-semantics matrix in C -- enforce/observe/
quick-enforce dispatch, JSON config, handler-signature validation,
stringize, trigger dispatch -- to prove the shared runtime behaves
identically from either front end; a reviewer checking behaviour should
spot-check a handful against their g++.dg counterparts rather than read all
of them.  `p4299-c-is-terminating-noexcept.C` is the one cross-language
test, a C++ TU that calls the C accessor `stdc_contract_violation_is_terminating`
over a `contract_violation` object to confirm the two front ends agree on
which semantics terminate, including P4298's `noexcept_enforce`.

Despite the shared-runtime design, using contracts from C is recorded in
the top-level `README`'s Known Limitations as currently requiring the
hosted C++ runtime library (`-lstdc++`) rather than a standalone C library;
nearly every test this commit adds carries a `dg-skip-if` gated on
`hostedlib` for that reason, even though the one auto-link line this commit
adds to the driver only names `-lcontracts`.

## Compile gap

This commit's C front-end additions do not themselves call forward into
anything unwritten: the new parser, decl and typeck code calls only the
shared runtime and shared `contracts-config` machinery that
`2200-libcontracts` and `2400-p3595` already provide, and none of it has a
C++ counterpart still to arrive.

One small thing is deferred rather than missing.  This commit widens the
`-fcontract-evaluation-semantic=` option record from `C++ ObjC++` to
`C C++ ObjC ObjC++` and, in the same hunk, drops the old help line; the
replacement help line spells out all seven semantics, naming P3100's
`assume` and P4298's two nonthrowing semantics in one string, so it cannot
be divided and lands in `6900-cross-paper-options`.  Between here and there
the option works in C and simply has no help text.

`-fcontracts-p4299` is deliberately absent from the `LangEnabledBy`
implication list -- it is the C front end's own flag and does not turn the
C++ facility on -- so the branch-wide implication gap recorded in
`6900-cross-paper-options` does not apply to this commit.
