## Rationale

Implement P3595, "Configuration of Contract Evaluation Semantics" -- a
compiler-only proposal, not a standards paper, so unlike the P-numbered
commits elsewhere on this branch it has no feature-test macro and no
`-fcontracts-pNNNN` gate of its own.  It is the mechanism by which a
contract's evaluation semantic (ignore/observe/enforce/quick_enforce/assume)
is chosen at compile time from something other than the hardcoded default:
by group, by source location, by an inline or file-supplied JSON
configuration, or -- the part with no precedent elsewhere on the branch -- by
a runtime selector resolved through a caller-supplied function.

Four things meet here. The **configuration format and source handling**:
`contracts-config.h/.cc` and `contracts-config-source.h` in both
`gcc/c-family` (the shared, language-independent JSON parsing and merge
logic) and `gcc/cp` (the C++-specific query construction), driven by four new
options -- `-fcontract-configuration=`, `-fcontract-configuration-file=`,
`-fcontract-group-evaluation-semantic=`, and the `-Wcontract-configuration`
warning for an accepted-but-suspect entry. The **query API**,
`contracts-config-query.h`: the `contract_query` a call site builds
(assertion kind, group names, caller vs. callee, in-constant-evaluation) and
the `contract_config_result` it gets back. **Compile-time semantic
selection**, `fill_query_groups`, `match_contract_specifiers`,
`has_active_contract_condition`, `contract_active_p` and friends, layered
onto the pre-existing (pre-branch) contract-wrapping machinery inherited from
upstream's own P2900 support. And the **P3595 dynamic-selection surface**:
`get_dynamic_selector_decl`, `resolve_dynamic_selector_namespace` and
`dynamic_selector_return_type` build the caller-visible selector function
(a plain C symbol or a qualified C++ name, cached so repeated mentions of the
same selector share one decl; `lookup_declared_dynamic_selector` looks a C++
name up as a qualified name, following inline namespaces, so a declared
selector is called by its own symbol); `contract_dynamic_provideweak` and
`emit_pending_weak_selectors` give it a weak default definition when the
configuration says one is wanted -- returning the entry's own `semantic`
as written (`contract_config_result::configured`, carried in the
descriptor as `contract_dynamic_configured_semantic`), since the dispatch
adjusts whatever the selector returns to the allowed set and the label's
`compute_semantic`, which need not be idempotent, and since one weak
definition serves every contract, label and translation unit sharing the
symbol -- after
`diagnose_mistyped_dynamic_selector` warns (`-Wcontract-configuration`)
about a declaration of a configured selector's name with another type; `build_contract_wrapper_function`,
`get_or_create_contract_wrapper_function`, `maybe_contract_wrap_call` and the
`find/get/set_wrapper_*` family extend the existing caller-side wrapping so a
call site can carry a dynamically-resolved semantic instead of a
statically-resolved one, keyed by `get_wrapper_tuple`/`caller_resolution`.

Group matching is by dotted prefix: an entry's group selects every group
whose name is its own followed by a dot, so `ub:expr.mul` selects
`ub:expr.mul.div.by.zero.int.div`.  A small table of combined groups
(`combined_contract_groups`, `group_selects_p`) names the groups that
select leaves outside their own name -- one,
`ub:conv.lval.valid.representation.bool.enum`, the name the P3100
invalid-value check reported before its `.bool` and `.enum` leaves.

This is also where the base contract-check emitter is reworked, because the
rework exists to serve dynamic selection: the rename to
`emit_check_for_semantic` with its `semantic` and `shared_data_addr`
parameters, the `unshare_expr` of the condition, the `if (shared_data_addr)`
reuse arm, and the new outer `build_contract_check` that dispatches on the
runtime selector's return value.  The test suite (over 100 files under
`p3595-*`, `ce-*`, `callerside-checks/` and `matrix-readers-*`) is
correspondingly the largest of any single commit on the branch: config
parsing and error diagnostics, group and line-range matching, caller-side vs.
dynamic-selector resolution, constexpr/template interaction, and multi-TU
tests that check two translation units calling the same dynamic selector
symbol agree.

A "C++"-linkage selector name is qualified from the global namespace: it is
resolved at the top level, since the check is built while the checked
function's namespace, and for a member function defined in its class the
class, is still the current scope (GCC-655,
`p3595-dynamic-selector-from-namespace.C`).

A dynamic selection never brings in a throwing semantic (observe or
enforce, whose violation handler may let an exception leave the check)
that the contract's allowed set does not hold
(`contract_semantics_nothrow_p`): under a label allowing neither, a
`compute_semantic` result outside the allowed set is an invalid selection,
as the static path rejects it, and an invalid selection is not reported
through the enforce entry point (`emit_enforced_violation`'s semantic):
with `-fcontracts-p4298` it is reported through the noexcept_enforce one,
and without it, where noexcept_enforce is unavailable, it traps as
quick_enforce whatever the label allows.

The caller-side wrappers, the dynamic tables and the other contracts maps
keyed by declarations hash a key with `contract_pch_hash` (by uid), so the
order in which `emit_contract_wrapper_func` defines the wrappers does not
depend on where trees are allocated, and `-g` does not change it
(`-fcompare-debug`; GCC-911, PR128021, `pr128021.C`).

The pre-existing `-fcontracts-client-check=` becomes configuration
entries appended after the configuration files, as P3595 maps it: `all`
is `{"match": {"caller": true}, "output": {"semantic": S}}` with S the
semantic of `-fcontract-evaluation-semantic=`, `pre` the same with
`"kind": "pre"`, and `none` ignores every caller-side query.  An entry with
no `caller` key, the catch-all from `-fcontract-evaluation-semantic=`
among them, matches callee-side queries only, so these entries are what
select a caller-side check when no file does
(`p3595-client-check-all.C`, `p3595-client-check-pre.C`,
`p3595-client-check-config-first.C`).

## Compile gap

One part is already settled.  The emitter rework this commit carries -- the
rename of the base emitter to
`emit_check_for_semantic` with its `semantic` and `shared_data_addr`
parameters, the `unshare_expr` of the condition, the `if (shared_data_addr)`
reuse arm, and the new outer `build_contract_check` that dispatches on the
runtime selector -- owes nothing: every `__cxa_` entry
point and data-block builder those lines call is already in place from
`2200-libcontracts`.

Beyond that: this commit's own functions do not call into the P3400
facet-label band (`resolve_contract_label`, `apply_label_string_facet`,
`apply_compute_semantic`, `ensure_contract_groups` and
`ensure_evaluation_semantic` all resolve to hunks owned by later commits in
the 4200-4290 range, confirmed by grepping their definitions out of the net
diff) -- so no stub is owed there.  That check was targeted at the P3400
names, because they are the ones a config/semantic-selection commit would
plausibly reach for; it is not a full identifier-by-identifier audit of
every function this commit's ~35 `contracts.cc` spans touch against every
other commit's spans.  If a narrower forward reference exists inside that
surface, it is not accounted for here.

One such reference is known: the invalid-selection arm of
`emit_dynamic_dispatch` reads `flag_contracts_p4298`, the variable
`4800-p4298`'s `c.opt` row defines, so this commit's `contracts.cc` does
not compile until then.  It matters only under a label, which `4200`
brings.

D4405's analysis evaluation adds two more, both to `4930-p4405-analysis`:
`contract_config_init` reads `flag_contract_analysis_semantic`, its
`c.opt` record, and `ensure_evaluation_semantic` calls
`label_analysis_semantic`.  Until then neither `cc1` nor `cc1plus`
compiles.
