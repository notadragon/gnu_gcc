## Rationale

Implement P3099, "User-Defined Diagnostic Messages" -- approved by EWG.  The
paper adds an optional string message to a contract assertion
(`pre(cond, "message")`), distinct from the `comment` GCC already
auto-generates from the condition's source text: `build_comment` is
untouched by this commit (it still populates `CONTRACT_COMMENT`); this
commit is only about the new, separate `CONTRACT_MESSAGE`.

Parsing is a new static `cp_parser_contract_message` (`parser.cc`): after the
condition, if `-fcontracts-p3099` is active and a comma follows, it consumes
the comma and defers to the pre-existing `cp_parser_diagnostic_message` --
the same parser GCC already uses for `static_assert`'s C++26 non-literal
message, from `2030-diagnostic-message-parser`.  It is called from the three
places a contract's condition is parsed -- a `contract_assert`, an ordinary
(non-deferred) function contract, and a late-parsed member-function
contract -- with the result threaded into `grok_contract`'s new trailing
`message` parameter for the first two, and into `finish_contract_message`
directly for the deferred case, since a deferred contract's condition (and
now its message) can only be finalized once the enclosing member function's
late parse completes.

`finish_contract_message` (`contracts.cc`) is the normalization step both
paths converge on: a message that already parsed as a string literal is used
as-is (after stripping any location wrapper); a message that is some other
constant expression -- the wording allows any expression convertible to and
constant-evaluable as a string, not only a literal -- goes through
`cexpr_str`, the same non-literal-constant-string validator GCC already
carries for `static_assert`'s message, to type-check and, once the
condition is no longer a `DEFERRED_PARSE`, constant-fold it down to a
`STRING_CST`.  The result is stored in `CONTRACT_MESSAGE` and is then run
through P3400's `compute_message` label facet via `apply_label_string_facet`
before being returned, so that whatever this commit produces, an
assertion-control label still gets a chance to transform it.  The function's
own comment states the invariant this establishes: `CONTRACT_MESSAGE` is
always either `NULL_TREE` or a bare `STRING_CST` by the time anything
downstream reads it, never a location-wrapped or unevaluated expression.

On the library side, `contract_violation::message()` (`contract26.cc`) reads
the `CXA_FIELD_MESSAGE` field and, unlike `comment()`, returns `nullptr`
rather than `""` when the field is absent -- this paper's own "Option C1",
keeping "no message supplied" distinct from an empty message, which matters
for a P3290 manual violation or a plain C `assert()`, neither of which
populates a message field at all.  `__cpp_contracts_message` (the compiler
macro) and its `contracts_message` entry in `version.def` are this paper's
feature-test pair; unlike P3290's vendor macro, this one gets a real
`__cpp_` name.

## Compile gap

`finish_contract_message` calls
`apply_label_string_facet (CONTRACT_LABEL (contract), "compute_message",
...)` to give an assertion-control label a chance to transform the message.
That function is P3400's; its definition belongs to
`4250-p3400-facet-string-transforms`, later in this history -- confirmed by
`4200-p3400-core`'s own Compile gap note, which lists it as one of the two
facet functions `resolve_contract_label` forward-references.  On its own,
this commit needs a declaration and a stub, and, as with `4200`'s own
trampoline stubs, the natural stub is quiet rather than loud:
`apply_label_string_facet`'s real early-return path (no label, or a label
that is not a class type) is `return current_val;` -- pass the message
through unchanged.  A stub with that same body is not an approximation of
the real function for this commit's own reachable inputs, it is exactly the
real function's behaviour for every one of them: `-fcontracts-p3400` and
assertion-control labels do not exist yet at this point in the linear
history, so `CONTRACT_LABEL (contract)` is never anything a stub would need
to treat differently.  `4250-p3400-facet-string-transforms` replaces the
stub once labels exist to actually route through it.

The library side owes nothing.  `contract_violation::message()` reads
through the `__cxa_find_field_ptr` / `CXA_FIELD_MESSAGE` mechanism in
`bits/contracts_abi.h`, and it is an out-of-line definition of a member
`contract_violation` must already declare; both the header and the
declaration land with `2200-libcontracts`, at band 2200.  That commit's own
default handler already prints `message()`, so it carries a `return
nullptr;` body for it -- recorded in its Compile gap -- which this commit
replaces with the real lookup.

**Behaviour gap: `-fcontracts-p3099` does not yet imply `-fcontracts`.**  The
`LangEnabledBy` expression that turns the base facility on is a single
boolean naming every per-paper flag at once, so it cannot be divided and
lands in `6900-cross-paper-options`.  Until that commit, `-fcontracts-p3099` sets its
own `flag_contracts_*` variable and nothing else, and this commit's own
tests -- which compile with it and expect contracts to be enabled -- fail.
The code is right; only the switch that arms it is missing.
