## Rationale

Implement P3098, "Postcondition Captures".  A plain `post` predicate only
sees the function's exit-time state; P3098 lets it also name a value as it
was at function *entry* -- `post [old = expr] (old == expr)` -- which the
base P2900 facility has no way to express.  Four places in the pipeline have
to agree on that.

* **Parsing** (`parser.cc`).  The capture list sits in a new slot between the
  contract's introducer and its predicate, and is parsed twice: a first pass
  inside `cp_parser_function_contract_specifier` validates the capture
  grammar and caches each init-capture's initializer tokens (reusing the
  default-argument token-caching machinery), then the cached initializers are
  parsed for real once the contract scope is open, so they see const-ified
  outer variables the way a precondition already does.  A capture's comma is
  genuinely ambiguous with a template-argument-list comma inside its own
  initializer (`[p = f<1, 2>()]`); the disambiguation is Core-issue-325's
  test applied inside the cache, and is worth a reviewer's look precisely
  because it is a peek, not a tentative parse.  `contract_assert` rejects a
  capture list outright (P3098 only extends `post`), and deferred (in-class)
  member-function postconditions defer the captures the same way they defer
  the predicate.

* **Construction** (`contracts.cc`), the bulk of the diff.
  `declare_outlined_capture_struct_locals` and `get_capture_struct_params` /
  `append_capture_struct_args` materialize the captures into a struct passed
  to the outlined `__post_fn` when `-fcontract-checks-outlined` is in play;
  the inline path instead threads them through
  `emit_preconditions_and_capture_inits_interleaved`, which is the one
  function actually named "interleaved": preconditions and capture
  initializers run in the lexical order P3098 requires, not preconditions
  first.  Captures are destroyed on *both* arms of the `TRY_FINALLY` /
  `EH_ELSE` pair `maybe_apply_function_contracts` builds around the body --
  the normal-return path via `emit_postcondition_capture_dtors` /
  `emit_outlined_capture_struct_dtors` after the predicate has run, and the
  exceptional path via the same functions with no predicate check at all --
  because a capture is itself a variable with a lifetime, exception or not.
  `remap_contract` / `copy_and_remap_contracts` extend the existing
  redeclaration-copying machinery to also remap a capture list onto a
  redeclaration's parameters.

* **`processing_postcondition_predicate`** (`cp-tree.h`, `parser.cc`, `pt.cc`)
  is a new scope_chain flag, true only while the predicate itself -- not the
  capture-list initializers -- is being parsed or substituted.  It exists
  because capture names are visible to the predicate but explicitly not to
  each other's initializers, so the boundary between "capture scope" and
  "predicate scope" has to be a real, save/restored piece of state, not an
  inferred one.

* **`semantics.cc`'s `process_outer_var_ref`** gains the carve-out that lets
  a predicate name a capture: a capture is a `VAR_DECL` already remapped to
  the instantiated function, and without the carve-out it looks exactly like
  a reference to an enclosing function's local.

* **`tree.cc`'s `cp_tree_equal`** gains a narrow special case: two artificial
  `VAR_DECL`s with the same name compare equal when `comparing_contracts` is
  set, which is what lets redeclaration matching reach a capture at all
  instead of trying to structurally compare two unrelated synthetic
  variables and always failing.  It only makes captures *comparable*; the
  actual "do these two capture lists match" check is one of the four
  field-comparisons `mismatched_contracts_p` adds in
  `4620-contract-extension-fields`, which depends on this commit for exactly
  that reason.

The test list is almost entirely P3098's own surface -- packs, member
captures, templates, `noexcept`, the `ignore` semantic, name lookup, and the
`-fno-exceptions` capture-destruction path -- plus the one P3098-only
re-entrancy test (`contract-reentrancy-p3098.C`); the P3097-crossed
re-entrancy tests live in `4010-p3097-p3098-combined` instead.

## Compile gap

None of this commit's own code is a forward reference: every symbol
`maybe_apply_function_contracts`,
`emit_preconditions_and_capture_inits_interleaved` and the rest of the
construction path call -- `apply_preconditions`,
`apply_postconditions`, `flag_contract_checks_outlined`,
`comparing_contracts`, `is_capture_proxy`, `current_lambda_expr` -- is part
of the base P2900 facility already present at the branch's root.  This is a
targeted check of the functions this entry's Contents names, not an
exhaustive audit of every call in `contracts.cc`.

**Behaviour gap: `-fcontracts-p3098` does not yet imply `-fcontracts`.**  The
`LangEnabledBy` expression that turns the base facility on is a single
boolean naming every per-paper flag at once, so it cannot be divided and
lands in `6900-cross-paper-options`.  Until that commit, `-fcontracts-p3098` sets its
own `flag_contracts_*` variable and nothing else, and this commit's own
tests -- which compile with it and expect contracts to be enabled -- fail.
The code is right; only the switch that arms it is missing.

`maybe_apply_function_contracts` is claimed here hunk by hunk rather than
whole.  The function is divided into sixteen separately-claimable hunks by
`anchors.py`, and three of the base-facility bug fixes inside it belong to
the P2900 band -- `1220-noexcept-body-wrapper-detected`
(GCC-24), `1230-lambda-capture-bind-through-statement-list` (GCC-16) and
`1140-retval-destroyed-on-unwind` (GCC-5 and GCC-44), each with its own
regression
test.  What is left here is the P3098 work: the outlined capture-struct
locals, the interleaved precondition-and-capture-init emission, and the
capture destructors on both arms of the `TRY_FINALLY`/`EH_ELSE` pair.

GCC-16 is listed above because half of it is genuinely this commit's
neighbourhood: the `process_outer_var_ref` carve-out that lets a predicate
name a capture proxy shares one hunk with the P3098 postcondition-capture
branch beside it, and it is reachable only once
`4640-contract-substitution-plumbing` substitutes a lambda's contracts at all,
so it would be dead code in the P2900 band.  GCC-16's other regression test,
`lambda-capture-contract-in-template.C`, is with the rest of that half in
`4640-contract-substitution-plumbing`, which is where the two-hop
capture-proxy bridge lives.
