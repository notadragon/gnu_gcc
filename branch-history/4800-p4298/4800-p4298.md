## Rationale

Implement P4298, "Nonthrowing Evaluation Semantics": two new evaluation
semantics, `noexcept_enforce` and `noexcept_observe`, that behave exactly
like `enforce` and `observe` except that the violation handler runs in a
non-throwing context -- a handler that exits by throwing terminates the
program instead of propagating the exception to the guarded function's
caller.  `-fcontracts-p4298` gates two new `EnumValue` rows for
`-fcontract-evaluation-semantic=` (`CES_NOEXCEPT_ENFORCE` /
`CES_NOEXCEPT_OBSERVE` in `contracts.h`), the `__cpp_contracts_nonthrowing_semantics`
compiler macro, and a `noexcept_observe` enumerator in libstdc++'s
`evaluation_semantic`.

Most of the compiler-side work is teaching the existing nonthrowing
machinery that these two semantics belong to it.
`contract_semantic_is_nonthrowing` and `all_contracts_statically_nonthrowing`
(`gcc/cp/contracts.cc`) are the predicates that decide whether an outlined
contract-check helper (a P3097 virtual-function wrapper, a P3595
caller/callee split) can itself be marked `noexcept`; both already existed
for `ignore`/`quick_enforce`/`assume`, and this commit is what adds
`noexcept_enforce`/`noexcept_observe` to the set, which is why the reviewer
should look there and at `contract_terminating_p`'s new
`CES_NOEXCEPT_ENFORCE` disjunct (`contracts.h`) rather than expect new
machinery.  The interaction tests reflect that: `p4298-noexcept-fn-p3097.C`,
`p4298-noexcept-fn-p3098.C`, `p4298-p3098-outlined-noexcept.C`,
`p4298-p3290-nothrow.C`, `p4298-p3400-is-nonthrowing.C` and
`matrix-exceptspec-p3400.C`'s sibling all check a paper this commit came
after, not new P4298 machinery.

The one genuinely new library surface is in the manual-trigger API P3290
added: an `inline namespace __p4298` overload set in `contract26.cc`
(`handle_enforced_contract_violation` / `handle_observed_contract_violation`,
taking `std::nothrow_t`) that reports the two new semantics instead of the
plain ones, so a caller compiled with `-fcontracts-p4298` gets nonthrowing
manual triggers with the same name lookup as before.

It also carries the three places in `libstdc++`'s runtime that name its two
semantics but sit inside `2200-libcontracts`' code: the `noexcept_observe`
and `noexcept_enforce` arms of the default violation handler's semantic
switch, and the third term of `contract_violation::is_terminating()`'s
disjunction.  Cuts in `branch-history/splits.md` carve all three out, so
`2200` reads as a runtime that knows only the four semantics that exist at
that point in the history -- its `default:` arm prints `unknown(N)` for the
other two, and its `is_terminating()` returns the right answer for the
semantics it knows.

## Compile gap

**Behaviour gap: `-fcontracts-p4298` does not yet imply `-fcontracts`.**  The
`LangEnabledBy` expression that turns the base facility on is a single
boolean naming every per-paper flag at once, so it cannot be divided and
lands in `6900-cross-paper-options`.  Until that commit, `-fcontracts-p4298` sets its
own `flag_contracts_*` variable and nothing else, and this commit's own
tests -- which compile with it and expect contracts to be enabled -- fail.
The code is right; only the switch that arms it is missing.

One further gap is this commit's alone.  The three `EnumValue` rows for
`-fcontract-evaluation-semantic=` are one hunk shared with P3100's `assume`,
and the three `EnumValue` marker lines in it are byte-identical, so the cut
declared in `branch-history/splits.md` cannot land on the boundary between
the papers and lands one line late.  This commit therefore receives its two
rows *without* the first of their two `EnumValue` markers, which stays with
P3100 in `6000-p3100-core`; at this point in the history `c.opt` has an
`Enum(contract_semantic) String(noexcept_observe)` line with no marker above
it, which `opt-gather.awk` will not accept.  It is repaired by
`6000-p3100-core` and the assembled file is correct.  Splitting the hunk
differently is not possible: a cut regex must match exactly one line of the
segment, and `^EnumValue$` matches three.

There is no third gap around the `_noexcept` entry points, and it is worth
saying so, because there nearly was one.  `emit_check_for_semantic` computes
`is_noexcept = (semantic == CES_NOEXCEPT_ENFORCE || semantic ==
CES_NOEXCEPT_OBSERVE)` and threads it into `declare_cxa_entry_point`, which
for a noexcept semantic asks `get_cxa_entry_point_name` for an extern symbol
named `__cxa_contract_violation_<kind>_<sem>_<mode>_noexcept`.
`libcontracts/dispatch.c` defines only the non-`_noexcept` half of that
symbol family, and says so in its own comment: "the _noexcept variants live
in the C++ runtime, which wraps these cores in a terminate-on-throw
barrier."  Those wrappers -- the `CXA_NOEXCEPT_OBSERVE` /
`CXA_NOEXCEPT_ENFORCE` macro expansions -- are in
`libstdc++-v3/src/c++26/contracts_abi.cc`, which this history attributes to
`2200-libcontracts` along with the rest of the violation ABI, so both halves
of the family are defined by the same commit and are in place 2,600 band
numbers before this one.  Because the two
`-fcontract-evaluation-semantic=noexcept_*` command-line spellings are
themselves this commit's own `EnumValue` rows, this is the first point in
the linear history where `is_noexcept` can ever become true -- and by then
there is nothing left to owe.  This commit's own `dg-do run` tests that
select `noexcept_enforce`/`noexcept_observe`
(`p4298-noexcept-enforce-abort.C`, `p4298-terminate-enforce.C`,
`p4298-terminate-observe.C`, and others) link standalone.  Where
`contracts_abi.cc` lands is what decides that, and a stub would not be an
honest substitute for it: the real definitions are a terminate-on-throw
`try { ... } catch (...) { std::terminate(); }` barrier around the existing
dispatch core, and getting that wrong changes observable behaviour -- whether
a throwing handler escapes or terminates.  The manual-trigger `__p4298`
overloads this commit adds are unaffected either way: they call the generic,
semantic-agnostic `__cxa_contract_violation` entry point rather than one of
the specialized symbols.
