# GCC-35: a declared-only template's contracts are never instantiated

**Status:** Open (defect -- missing diagnostic)
**Kind:** defect
**Component:** c++ / contracts
**Upstream Link:** `--` (reachable only with `-fcontracts`, which is upstream,
but the shape depends on our on-use instantiation model; see "Is this
upstream's?" below)
**Found:** 2026-09-05, by the `sfinae` group of `contract-matrix-gen.py`, cell
`odr_used_illformed_predicate_is_an_error`.

## Symptom

An ill-formed contract predicate on a function template that is **declared but
never defined**, and is called, is silently accepted.

```c++
template <class T> int f (T t) pre (t.nonexistent ());
int use () { return f (0); }
```

```
g++   -std=c++26 -fcontracts -fsyntax-only   ->  accepted
clang -std=c++26 -fcontracts -fsyntax-only   ->  error: member reference base
                                                 type 'const int' is not a
                                                 structure or union
```

Reproducer:
[`gcc-35-declared-only-template-contract-not-instantiated.C`](gcc-35-declared-only-template-contract-not-instantiated.C).

## Why it happens

GCC substitutes a function's contracts in `instantiate_body`. There is no
definition here, so that never runs.

GCC-34 fixed the adjacent case -- a P3097 wrapper or a P3595 caller-side check
needing the contracts of a function that is never defined -- by calling
`maybe_instantiate_contracts` from `define_one_contract_wrapper_func`. That is
the only caller. With plain callee-side checking there is no wrapper, so
nothing reaches the predicate.

[dcl.contract.func]/9 puts the odr-use and the definition on the same footing:
the contract assertions are needed at **either**. Clang acts on that in
`InstantiateFunctionContractsOnUse`, whose own comment names this exact case
("a declaration-only template that is called: the predicate stays dependent").

## Severity: diagnostics only

Nothing goes silently unchecked at run time. With no definition in this
translation unit and callee-side checking, GCC emits no check for `f` either
way -- the check belongs to the definition, wherever that is, and will be
diagnosed there. So this is a missing diagnostic, not a missing check.

Two things bound it further:

* the **[dcl.contract.func]/7** const-parameter rule *is* applied to this
  shape by GCC (`template <class T> int g (T t) post (r: t == r);` called with
  an `int` is correctly rejected), because that check runs at declaration time
  rather than through contract instantiation;
* turning on P3595 caller-side checking, or making the function virtual under
  P3097, routes through the wrapper and therefore through GCC-34's fix, so
  those shapes are already correct.

## Is this upstream's?

Not measured, and not obviously meaningful to measure. Plain `-fcontracts` is
upstream, so a stock trunk build could in principle be asked -- but upstream
has neither the on-use instantiation nor the wrapper paths that frame the
question, so a stock answer would not tell us whether *our* model is
self-consistent. Marked `--` on the grounds that the defect is in the seam
GCC-34 opened rather than in stock behaviour. Worth a stock measurement before
any decision to file.

## The judgement call

Recorded as `defect` rather than `divergence` because [dcl.contract.func]/9
does name the odr-use, so the two compilers are not equally defensible. There
is room to read "needed" as not compelling instantiation of a predicate whose
check is never emitted, in which case this becomes `divergence` and probably
`deferred`. That reclassification is the user's to make.

## Clang
